### 1.1. 기능 누락

| Gap ID | 누락 항목 | 출처 | 심각도 | 핵심 가치 필수? | 조치 방안 |
|:---|:---|:---|:---|:---|:---|
| **OMI-001** | `game_libraries` 테이블 (게임별 플레이 시간·업적을 DB에 영구 저장) | Architecture ERD §3.1 | 🟡 중간 | **No** | 현재 외부 API에서 실시간 조회하는 구조로 대체됨. 설계 문서에서 공식 제외 처리하고, 현 구조를 역방향 반영 |
| **OMI-002** | AES-256 암호화 (외부 토큰, PII 데이터) | SRS §4.2, FSD §5, AC-05 | 🔴 높음 | **Yes** | 비밀번호는 PBKDF2(SHA-512) 해싱으로 안전하게 처리되고 있으나, 명세의 AES-256 요구사항은 충족하지 못함. 현재 외부 토큰을 저장하지 않으므로 실질적 리스크는 낮음. **SRS를 수정하여 현 구현(PBKDF2)을 명시** |

| **OMI-005** | CSRF 토큰 방어 | FSD §5 (Security) | 🟡 중간 | **No** | JWT Bearer Token 방식은 CSRF에 본질적으로 면역. SPA + API 구조에서는 CSRF 토큰이 불필요. **설계 문서에 면제 사유 기록** |
| **OMI-006** | 하드웨어 마스터 카탈로그 정규화 매핑 | SRS §2.2.2, FSD §3.2 | 🟡 중간 | **No** | 현재 사용자가 직접 텍스트 입력 → express-validator로 검증하는 구조. 유사 명칭 제안/자동완성 기능은 미구현. 2단계 이관 |
| **OMI-007** | 매칭 결과에 상세 그래픽 옵션 개별 출력 (Texture, Shadow, Ray-Tracing 등) | FSD §3.3 | 🟢 낮음 | **No** | 현재 `settings_json` JSONB에 통합 저장되어 있으며, UI에서 JSON 키-값을 파싱하여 표시. 개별 필드 분리는 2단계 |

## 3. 설계 산출물 불일치 분석 (Architectural Drift)

> 코드는 정상 동작하나 설계 문서와 구조가 다른 항목

| Drift ID | 분류 | 설계 문서 | 현재 구현 | 원인 | 조치 방안 |
|:---|:---|:---|:---|:---|:---|
| **DFT-001** | ERD 불일치 | `users` 테이블: 4개 컬럼 (id, provider, provider_id, created_at) | 13개 컬럼으로 확장 (email, nickname, password_hash, email_verified, role, is_banned, linked_providers, subscription_status, toss_payment_key 추가) | 로컬 회원가입, 관리자 기능, 결제 기능 추가에 따른 자연적 확장 | **ERD를 현재 스키마 기준으로 최신화** |
| **DFT-002** | ERD 불일치 | `game_libraries` 테이블 존재 | 미구현 (외부 API 실시간 조회로 대체) | 설계 시 DB 영구 저장 전제 → 구현 시 API 직접 호출로 변경 | **ERD에서 제거하고 "External API Direct Query" 구조로 문서화** |
| **DFT-003** | ERD 추가 | 미설계 | `posts`, `comments`, `post_likes`, `email_verification_codes` 4개 테이블 추가 | 커뮤니티·인증 기능 추가 | **ERD에 4개 테이블 역방향 추가** |
| **DFT-004** | 알고리즘 차이 | 가중치: GPU 50%, 해상도 30%, CPU 10%, RAM 10% / Threshold 0.9 | 가중치: GPU 50%, CPU 30%, RAM 10%, 해상도 10% / Threshold 0.8 | 실제 매칭 성능 튜닝 과정에서 CPU 중요도 상향 조정 | **FSD/SRS를 현재 구현 기준으로 수정** |
| **DFT-005** | 배포 환경 | Docker + Kubernetes + AWS | Vercel Serverless Functions | 비용/복잡도 고려한 현실적 판단 | **Architecture 문서를 Vercel 기반으로 전면 수정** |
| **DFT-006** | 캐싱 | Redis In-Memory Cache | In-Memory Fallback DB (mockDb.js) | Redis 미도입 | **Architecture 문서에 현재 Fallback 구조 명시** |
| **DFT-007** | 보안 | AES-256 양방향 암호화 | PBKDF2(SHA-512) 단방향 해싱 | 비밀번호는 해싱이 더 안전한 선택 | **SRS 보안 섹션에 PBKDF2 채택 사유 명시** |
