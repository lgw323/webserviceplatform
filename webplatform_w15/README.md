구체적으로는 다음 4단계를 수행했습니다:

```
[Phase 1] 지금 앱에 뭐가 있는지 전부 목록화

[Phase 2] 처음 기획과 지금 코드를 1:1 매핑

      ↓
[Phase 4] ERD/아키텍처 도면을 현재 기준으로 갱신 + 테스트
```

## ⚠️ "있긴 한데 약간 다른" 3가지가 뭔가

### 1. 이메일 인증 — 콘솔에만 찍히고 실제 메일은 안 감

- **기획**: 이메일 인증 코드를 사용자 메일로 발송
- **현재**: 인증 코드가 **서버 콘솔에 출력**될 뿐, 실제 SMTP(이메일 발송 서버)는 연결 안 됨
- **영향**: 테스트 환경에서는 문제 없지만, 실제 서비스에서는 유저가 코드를 볼 수 없음
- **심각도**: 중간 — 실서비스 전환 시 SMTP 연동 필요

### 2. 매칭 알고리즘 가중치 — 기획서와 숫자가 다름

- **기획(FSD 원문)**: GPU 50%, 해상도 30%, CPU 10%, RAM 10%
- **현재 코드**: GPU 50%, **CPU 30%**, RAM 10%, **해상도 10%**
- **왜 달라졌나**: 실제 매칭 테스트 과정에서 CPU 중요도가 해상도보다 높다고 판단하여 조정함
- **영향**: 매칭 결과의 순서가 원 기획과 다를 수 있음
- **심각도**: 낮음 — 현재 구현이 실질적으로 더 합리적

### 3. 유사도 필터 기준값 — 90%가 아니라 80%

- **기획**: 유사도 0.9(90%) 이상인 결과만 보여줘야 함
- **현재 코드**: 기본값이 **0.8(80%)** 으로 설정됨
- **왜 달라졌나**: 90%로 잡으면 보여줄 결과가 너무 적어서 완화함
- **영향**: 사용자에게 더 많은 결과가 보이지만, 정확도가 약간 낮은 결과도 포함됨
- **심각도**: 낮음 — API 호출 시 `threshold=0.9` 파라미터로 원래 기준 적용 가능

개발하면서 기획에 없던 기능이 11개 추가되었습니다. 이것들은 전부 **사용자에게 도움이 되는 기능**이므로 삭제할 필요 없이, 대신 기획서/설계서에 역으로 반영하여 문서 정합성을 맞춰야 합니다.

| # | 추가된 기능 | 왜 추가됐는지 | 문제 있는지 |
|:-:|:---|:---|:---|
| 1 | **커뮤니티 게시판** (글쓰기/수정/삭제 + 좋아요 + 댓글) | 사용자 간 소통 공간 필요 | ✅ 문제 없음 |
| 2 | **토스페이먼츠 결제 + 프리미엄 구독** | PRD 수익모델(프리미엄 구독) 실현 | ✅ 문제 없음 |
| 3 | **프리미엄 전용 상위 1% 통계 위젯** | 프리미엄 유저에게 차별화 콘텐츠 제공 | ⚠️ **주의** — 지금은 가짜(Mock) 데이터만 보여주고 있어서, UI에 "데모 데이터" 표시가 필요 |
| 4 | **하드웨어 병목 기반 업그레이드 광고** | PRD 수익모델(타겟 광고) 실현 | ✅ 문제 없음 |
| 5 | **다크/라이트 테마** | UX 품질 향상 | ✅ 문제 없음 |
| 6 | **실시간 검색 + 알림 시스템** | UX 품질 향상 | ✅ 문제 없음 |
| 7 | **인메모리 Fallback DB** | PostgreSQL 연결 안 될 때도 앱이 돌아가도록 | ✅ 문제 없음 |
| 8 | **웹접근성(WCAG 2.1) + SEO 최적화** | 비기능 품질 향상 | ✅ 문제 없음 |
| 9 | **소셜 로그인 Fallback** (API Key 없어도 동작) | Vercel 배포 시 API Key 없이도 테스트 가능 | ✅ 문제 없음 |
| 10 | **외부 계정 연동(Link) / 해제(Unlink)** | Steam·Riot 계정을 기존 계정에 묶는 기능 | ✅ 문제 없음 |
| 11 | **관리자 게시글/댓글 관리** (숨기기, 삭제) | 관리 기능 확장 | ✅ 문제 없음 |

## ❌ 기획서에 있었는데 안 만들어진 것 7가지

"완전 누락된 핵심 기능"은 0개이지만, **기획서에 언급은 되어있으나 만들어지지 않은 세부 항목**이 7가지 있습니다. 대부분은 **현실적인 이유로 대안이 채택된 경우**입니다.

| # | 기획서에 쓰여있던 것 | 현재 상태 | 왜 안 만들었나 / 어떻게 대체했나 | 앞으로 필요한가 |
|:-:|:---|:---|:---|:---|
| 1 | `game_libraries` 테이블 (게임 데이터를 DB에 저장) | **미구현** | Steam/Riot API에서 실시간으로 가져오는 방식으로 대체. DB에 따로 저장할 필요가 없어짐 | ❌ 불필요 — 설계서에서 삭제 처리 |
| 2 | AES-256 암호화 (비밀번호·토큰 암호화) | **다른 방식 적용** | 비밀번호는 PBKDF2(SHA-512)로 해싱 — 이건 업계 표준이고 AES-256보다 비밀번호 저장에는 더 적합함. 외부 토큰은 DB에 저장하지 않으므로 암호화 대상 자체가 없음 | ❌ 불필요 — 설계서를 현재 방식으로 수정 |
| 3 | Redis 캐싱 (응답속도 100ms 이내 보장) | **미도입** | Vercel Serverless 환경에서 Redis 붙이려면 비용·복잡도가 높음. 현재는 인메모리 Fallback이 일부 캐싱 역할 수행 | 🟡 나중에 — Vercel KV 등으로 도입 가능 |
| 4 | Docker + Kubernetes 배포 | **Vercel로 대체** | 1인 프로젝트에서 K8s는 과도함. Vercel이 무중단 배포·오토스케일링을 자동 처리 | ❌ 불필요 — 설계서를 Vercel로 수정 |
| 5 | CSRF 토큰 방어 | **미구현 (불필요)** | JWT Bearer Token 방식은 CSRF 공격에 원래 면역. SPA + API 구조에서는 CSRF 토큰이 필요 없음 | ❌ 불필요 — 설계서에 면제 사유 기록 |
| 6 | 하드웨어 마스터 카탈로그 (자동완성·정규화) | **미구현** | 현재는 사용자가 직접 텍스트 입력하고 express-validator로 형식만 검증. 자동완성·유사 명칭 제안 기능은 없음 | 🟡 나중에 — UX 개선 시 도입 가치 있음 |
| 7 | 매칭 결과에 개별 그래픽 옵션 표시 (Texture, Shadow 등) | **부분 구현** | `settings_json`에 통합 저장되어 있고 UI에서 JSON을 파싱해서 보여줌. 별도 필드로 분리하진 않음 | 🟢 현재로도 충분 |

| # | 어디서 | 무슨 문제 | 쉽게 말하면 |

## 📐 설계 문서랑 달라진 것 7가지

코드는 정상 동작하지만, 처음 설계 문서(ERD, 아키텍처)와 구조가 달라진 항목입니다. Phase 4에서 설계 도면을 현재 코드 기준으로 새로 그려서 동기화했습니다.

| # | 뭐가 달라졌나 | 처음 설계 | 현재 구현 |
|:-:|:---|:---|:---|
| 1 | `users` 테이블 컬럼 수 | 4개 (id, provider, provider_id, created_at) | **13개**로 확장 (email, nickname, role, is_banned 등 9개 추가) |
| 2 | `game_libraries` 테이블 | 있었음 | **삭제** — 외부 API 실시간 조회로 대체 |
| 3 | DB 테이블 수 | 5개 | **8개** — posts, comments, post_likes, email_verification_codes 추가 |
| 4 | 매칭 가중치 | GPU 50 / 해상도 30 / CPU 10 / RAM 10 | GPU 50 / **CPU 30** / RAM 10 / **해상도 10** |
| 5 | 배포 환경 | Docker + Kubernetes + AWS | **Vercel Serverless** |
| 6 | 캐싱 | Redis | **인메모리 Fallback DB** |
| 7 | 비밀번호 암호화 | AES-256 | **PBKDF2(SHA-512) 해싱** |
